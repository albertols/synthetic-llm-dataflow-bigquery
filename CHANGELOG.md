# Changelog

What changed in each tagged release, in [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) shape. Versions follow [SemVer](https://semver.org/spec/v2.0.0.html), minted from the squash-merge title by [`release_tag_report.yaml`](.github/workflows/release_tag_report.yaml).

**This file is the source of the GitHub Release notes.** At tag time the Action promotes `[Unreleased]` to a dated section with [`scripts/release/make_release_notes.py`](scripts/release/make_release_notes.py) and publishes that exact text — so the page and this file cannot drift. Write bullets under `[Unreleased]` as work lands; categories left empty are dropped on promotion, and repo-relative links are pinned at the tag when published.

Measured numbers behind these releases live in [`docs/releases/`](docs/releases/README.md) (one deterministic before/after report per version); decisions live in [`docs/adr/`](docs/adr/).

## [Unreleased]

### 🚀 Added
- **The evaluator reads its tables without `bigquery.readsessions.create`.** A launch in a deployment whose worker account lacks `roles/bigquery.readSessionUser` failed on every read (`DIRECT_READ` opens a Storage Read API session on the read table's project). The launch now asks for one read session per project of the planned read tables, after the prepare statements and before the graph: a read table is paged if and only if its project refused (a 403), through the BigQuery client's `tabledata.list` by row ranges, with `bigquery.tables.get` and `bigquery.tables.getData` and no read session; every other read table keeps `DIRECT_READ`; any other answer fails the launch. One `WARNING` names each refusing project and the table sides it pages, with their rows and bytes, and the registry row keeps it. No parameter, no DAG change, no template change. A table that changes while it is paged fails the job instead of being read wrong, and a table is read as empty only when `tabledata.list` itself counts no row; a throttled page waits by the error's reason. Paging is slower (BigQuery's `tabledata.list` quota, charged to the project that contains the table): `--mode sampled` is the lever for large tables ([ADR 0041, note of 2026-10-10](docs/adr/0041-evaluation-standalone-package.md), design §5.2). Not yet run against BigQuery.
- The evaluation launch times what is inside its submission: `free text pools`, `pipeline options`, `graph` and `pipeline run`, then their sum `submission`, and a `read path` line before them; Beam's own `Starting GCS upload` / `Completed GCS upload` lines are relayed while the pipeline is handed to its runner.
- The standalone evaluation DAG (`composer/evaluation_framework.py`) evaluates a landed run on its own by the chain's seed path, reading no job log: params `seed_table`, `source_dataset`, `landing_dataset`, `scope`, `reference_rows_limit` and `validation_runs_table` (defaults from three markers the generation DAG already uses), with `generation_job_id` as the launch's identity when known; four shapes of trigger, each rendered into a legal launch (a typed `run_id` or `tables` beats the default seed); a list of jobs (`generation_job_ids`) stays the full lookup of each job, the seed is not handed to the runs it starts. Its tasks no longer pass `deferrable`: the sensor waits in reschedule mode and the launch keeps `wait_until_finished`. Both evaluation launches take a launcher machine type (`launcher_machine_type`, `evaluation_launcher_machine_type`; default `e2-standard-8`; REST `environment.launcherMachineType`), because a Flex Template launch has 12 minutes in all, the image pull included, and the public REST description has no field for the limit itself ([ADR 0041](docs/adr/0041-evaluation-standalone-package.md), note of 2026-10-09).
- Planning says where its time goes: `sdfb-eval` (and the flex entry) print one line per planning step and table with its seconds (`planning <id> <table>: locate 0.42s`, then source pin, planning tables, planning statistics, scope verification, reference panel, sampling; dry runs and census for all tables; read-only parents) and a summary with the number of BigQuery statements by kind; the driver adds the target check, the launch lookup, the relationship models, the RUNNING row, the prepare statements and the submission. On a Flex Template launch everything before the Dataflow job exists runs on the launcher VM, which Google limits to 12 minutes including the image pull, so these lines are how a slow launch is diagnosed. Table names only: no SQL, no value.
- `sdfb-eval --seed_table T` evaluates what a launch of table T generated: T's enabled component in the relationship model (`--relationships_uri`), parents first, or T alone when no model names it, none is given, or the URI holds no model file (a warning says so). With `--relationships_uri` alone the evaluator names all the model's enabled tables. Each landing table is read whole (`scope=manual`; with `write_disposition` append that includes earlier launches' rows), the generation's `reference_rows_limit` and `validation_runs_table` are passed (new flags `--reference_rows_limit` and `--validation_runs_table`, both shared with the generator in the template): with the job's window, this launch's `validation_runs` rows (one query) verify the rebuilt reference sample, so the reference-based privacy metrics (the nearest-neighbour ones and the panel-based match rates and lifts) are evaluated; without the table or the window they are not evaluated, with the reason, a table that cannot be read is skipped with a warning and only a target with no readable table fails. The generation DAG's chained evaluation uses it: it passes `seed_table`, `relationships_uri` (empty when `generate_fk_relationships` is false), the landing dataset and a new `source_dataset` param and the generation job id as the launch's identity (`--generation_job_id` may accompany `--seed_table`: the evaluator reads the Dataflow job resource for its window, never the log or BigQuery job labels), so it reads no job log and its service account needs `roles/dataflow.viewer` (without it a warning and no window) but neither `roles/logging.viewer` nor `roles/bigquery.resourceViewer`; the row carries the job id and window and is listed in `evaluation_latest_per_job`. Cost: a model the launch adjusted is not seen, and the table list is the seed's; the window pins the source as of the job's create time ([ADR 0041](docs/adr/0041-evaluation-standalone-package.md), note of 2026-10-08).
- `packages/sdfb-evaluation` ([ADR 0041](docs/adr/0041-evaluation-standalone-package.md)): a standalone evaluator (its own lock and Python pin, excluded from the uv workspace) that scores landed tables against the full source in a separate CPU job and writes `evaluation_data_history`, `evaluation_metrics`, `evaluation_profiles` and `evaluation_row_flags` plus two views to `synthetic_data_quality`. The `sdfb-eval` command (`plan`, `run`, `report`, `compare`, `catalogue`, `schemas`), a flex-template entry, a Composer DAG (`composer/evaluation_framework.py`, chained from the generation DAG) and one metric catalogue as the single source of truth. A sampled run never stores a sample's number as exact: a row computed from a sampled side says `method = sample` with its rate, and a metric that needs every row of a side is `not_evaluated` with the reason. A profile's histogram edges are at least 10 source records apart and its quantiles at least 10 of that side's records apart. The registry holds one terminal row per evaluation, whoever writes it (the pipeline, the command or the Composer callback). Built and reviewed on a laptop with invented data; **not yet run on Google Cloud**.
- `.claude/skills/evaluation-framework/SKILL.md`: when to run the evaluator, reading baselines, noise floors and lifts, extending the catalogue.
- **One image, one template, one DAG import for generation and evaluation** ([ADR 0041, amendment of 2026-10-06](docs/adr/0041-evaluation-standalone-package.md#amendment-2026-10-06-one-image-one-template)). `docker/Dockerfile` also carries the evaluator's source (through a build stage that tolerates its absence, so a tree without `packages/sdfb-evaluation` still builds), on the generator's environment; a build step imports the evaluator's entry modules so a missing dependency fails the build. The template's entry is a dispatcher, [`docker/flex_entry.py`](docker/flex_entry.py): the template parameter `sdfb_job=evaluation` runs the evaluator, and a launch without it is a generation launch, as before. Not built or launched yet.
- The generation DAG evaluates its own run when `run_evaluation` is true: `start_sdfb >> run_evaluation_gate >> wait_for_generation >> trigger_evaluation >> wait_for_evaluation_launch`. The waits are reschedule-mode sensors (no triggerer needed); the evaluation is a second, CPU-only launch of the same template, and the last task waits only until that job runs. New params `evaluation_mode`, `evaluation_machine_type`, `evaluation_max_workers`, `evaluation_output_dataset`; no new marker and no new Airflow Variable. With `run_evaluation` false the DAG does what it did.
- The standalone evaluation DAG accepts `generation_job_ids`, a list: it starts one run of itself per job id (one Dataflow job each, one after another) and leaves the per-job path as it was.
- `disk_size_gb`, Beam's own worker boot disk, is a declared template parameter: an evaluation launch on the shared multi-GB image passes 200, the size the generator pins for itself.
- **Synthetic Platform**, a local-first GUI in [`gui/`](gui/README.md) ([ADR 0042](docs/adr/0042-self-hosted-platform-gui.md)): a React app and a Fastify backend bound to `127.0.0.1` that read and explain the project's data in four tabs. INTRO tours the pipeline; EVALUATION lists evaluations, drills into one run and compares runs; RAG shows the 384-d space, the embedder lab, the FAISS index, the seed strategies and the free-text pools; CONFIG holds the Pipeline amp (every knob with its value from the code), the scenario calculator, the source-stats explorer and the guardrails. It runs on a seeded mock with no GCP access, or reads `synthetic_data_quality.*` and `synthetic_rag.*` through named, read-only queries that are dry-run first and capped by `MAX_BYTES_BILLED` (10 GiB by default); fetched rows stay in memory.
- The GUI's types are generated from the Python side: the BigQuery schemas, the metric catalogue, [`scripts/gui/export_knobs.py`](scripts/gui/export_knobs.py) (knobs, the evaluator's `sdfb-eval` flags read from its CLI, sample relationship models, DLQ rules) and [`scripts/gui/export_golden_fixtures.py`](scripts/gui/export_golden_fixtures.py), whose golden files pin the TypeScript ports of the hashing embedder, GReaT serialization, retrieval, the evaluator's scorer and the run-to-run verdicts of `sdfb-eval compare` (the compare view reads "≈" by the same rule). `npm run contracts:check` and the exporters' `--check` fail CI on drift. A golden file is the same on every machine (its `python` stamp is the minor version, not the patch).
- [`.github/workflows/gui.yml`](.github/workflows/gui.yml): typecheck, lint, unit tests, build, bundle budgets, contract drift, the tab-ownership gate, and Playwright + axe at 1440 and 390 px, plus an `exports` job for the Python exporters.
- **The GUI shows a launch's model adjustments ([ADR 0038](docs/adr/0038-measured-conflicts-adjust-the-model.md)) next to the evaluator's PK-duplicate verdict.** A PK duplicate rate on a key the launch dropped because the source repeats it read as a bare FAIL; the run view now reads the generator's own `validation_runs` row beside it (read-only, `GET /api/evaluations/:id/adjustments`): an `Adjusted` pill (faithful, under- or over-reproduced, or `Adjusted?` when the row cannot be joined or measured no share) with both key-repeat shares, their difference and the tolerance, in the interpretation, the scorecards, a new "Model adjustments" section of the Relational tab, the model graph and the parameters, and in CONFIG's guardrails. The evaluator's row, status and counts are not changed and stay on screen; a table the evaluator passed but whose copy missed gains a warning; a registry row that names an evaluator job as its generation job gets a callout. The mock gains one such launch under aliased table names ([how it reads](gui/docs/UX.md#adjusted-keys-adr-0038)). Not yet run against BigQuery.

### 🔧 Changed
- **A run of the generation DAG evaluates itself by default.** `run_evaluation` defaults to true (it was false) and `evaluation_max_workers` to 8 (it was 4) in [`composer/synthetic_beam_bigquery.py`](composer/synthetic_beam_bigquery.py). A trigger with no parameters now also launches the CPU evaluation job, keeps the DAG's one run slot until the generation job has ended and the evaluation's launch is over, and is marked failed when that launch dies; it needs the evaluation tables and views and the evaluator's roles ([`docs/DEPLOYMENT_PREREQUISITES.md`](docs/DEPLOYMENT_PREREQUISITES.md)). Trigger with `run_evaluation` false to launch generation alone, as before. The standalone DAG's `max_workers` is unchanged ([ADR 0041](docs/adr/0041-evaluation-standalone-package.md), note of 2026-10-14). Not run on a deployment.
- `docker/flex_template_metadata.json` declares the generator's parameters, `sdfb_job` and the evaluator's, and **every parameter is optional**: a launch for one job cannot be made to supply the other's. A generation launch that lacks a required flag is now refused by the generator's own argument parser in the launcher, not by the Dataflow API. `run_id` no longer carries a pattern (both jobs take any text there).
- `composer/evaluation_framework.py` launches from the generation template and reads the marker the import workflow already substitutes for the generation DAG; it needs no marker of its own.
- `packages/sdfb-evaluation/deploy/build_flex_template.sh` builds only an evaluator-only template from an existing image (`IMAGE=…`); it builds no image. The package's CPU `Dockerfile` stays for the package as a unit of its own.
- Preflight step 13j looks for the deployment's one template (`sdfb-<version>-template.json` or `sdfb-latest-template.json`), an evaluator-only template, or any `sdfb-*-template.json`, and names what it found.
- The generation launcher's log lines carry the logger name `sdfb_beam.cli.run_pipeline` where they carried `__main__`: the launch now enters through the dispatcher.
- The generation DAG's `sdk_containers` default is `multi` (it was `single`): one SDK process per vCPU, the topology [ADR 0034](docs/adr/0034-generation-throughput-single-barrier-shared-engines.md) measured at three times the fleet rate. Pass `single` to pin one process per worker. The personal-GCP tiers keep `single`. The GUI's config page follows the DAG: its presets estimate from the R7 multi run, and the switch to multi is recommended only from `single`.
- The standalone evaluation DAG's `max_workers` default is 8 (it was 4), and at least 4.
- **Where an evaluation's reference panel is on Dataflow** (the design's accepted channel 4): objects under the job's temp location, read by the workers, and no longer in the job graph; a local run still embeds it. The launcher therefore creates objects under the temp location (until now it wrote only under the staging one), the temp location holds source rows (restrict it and give it a lifecycle rule: the objects are not deleted when the job ends), and a launch that cannot write there fails before it submits, with a `FAILED` registry row. The design also said the graph was an object in the job's bucket only with `upload_graph`; Beam stages `pipeline.pb` there for every Dataflow job, so the panel rows have been in that bucket since the first launch.
- CLAUDE.md constraint 3 and ADR 0001 are narrowed to managed dashboard services (Looker, Looker Studio / Data Studio, Dataplex): a self-hosted GUI may read the project's tables, read-only ([ADR 0042](docs/adr/0042-self-hosted-platform-gui.md)). `gui/**` and `scripts/gui/**` stay out of the Dataflow Solution Guides copy.
- Python 3.14 and Apache Beam 2.76, the baseline of the Dataflow Solution Guides ([PR #289 review](https://github.com/GoogleCloudPlatform/dataflow-solution-guides/pull/289#issuecomment-5837875462)): `.python-version`, `requires-python` (`>=3.14,<3.15`), ruff and mypy targets, CI, the Beam SDK image (`apache/beam_python3.14_sdk:2.76.0`) with `apache-beam[gcp]==2.76.0` in lockstep, the Flex Template launcher base (`python314-template-launcher-base`), the image's site-packages bridge, and both model-staging Cloud Build steps (`python:3.14-slim`). The rebuilt image needs a Dataflow run before the next DSG sync ([ADR 0040](docs/adr/0040-dsg-donation-golden-source-sync.md) A6).
- The `inconsistent-quotes` pragma in 47 modules now gives its real reason: yapf 0.43, the latest release and the DSG's pin, cannot parse f-strings that reuse their own quotes ([PEP 701](https://peps.python.org/pep-0701/)), so the fields keep single quotes on 3.14 too.
- **The evaluator moves with the shared image**: `packages/sdfb-evaluation` pins Python 3.14 and `apache-beam[gcp]==2.76.0` (its `.python-version`, `requires-python`, mypy target and lock, the package's own `docker/Dockerfile`, its CI job), because the one image runs it on the generator's environment. Its Python and Beam can no longer be bumped alone: three tests hold them equal to the generator's ([ADR 0041, amendment of 2026-10-13](docs/adr/0041-evaluation-standalone-package.md#amendment-2026-10-13-python-314-and-beam-276-with-the-shared-image)). No evaluator logic changed. The GUI workflow's `exports` job runs on 3.14 and the five golden files carry the `3.14` stamp; nothing else in them changed. Resolved and tested on a laptop; the image has not been rebuilt and no job has run on it.

### ⚡ Performance
- **An evaluation launch plans its tables at once.** The planning scans of the tables (each side's planning statistics, the row-count check and the reference panel) ran one table after another, inside a Flex Template launch's 12 minutes: on the first chained evaluation of a full-size run they took 308 s of a 320 s planning and the launch did not fit ([ADR 0041, note of 2026-10-11](docs/adr/0041-evaluation-standalone-package.md), with the figure). They now run on up to eight threads; sampling and everything after it stay in table order once every scan has ended, so the plan is the same whichever scan ends first, and a failing table raises its own error after the others have ended (their statements have been billed by then; a second failing table is logged as a warning). An interrupt stops the scans: nothing further is sent. A new line times the phase, `planning <id> (all tables): scans <s>s`; the per-table lines keep their shape and now overlap.
- **On Dataflow the reference panel is staged beside the job graph instead of embedded in it.** The R and H rows, the census's views of them and each table's panel hashes and privacy inputs were `beam.Create` constants, so the graph a launcher builds, serialises, rebuilds and serialises again grew with tables x panel rows (44 MB at 10,000 reference rows over five tables). The launch now writes each payload as one object under `<temp_location>/sdfb-evaluation/<evaluation_id>/panel/` and the graph carries the object's name, sha256 and element count; a worker checks the digest before it unpickles the object and the count after. The launch says `evaluation <id>: panel staging: <n> objects, <size>, <s>s (<w>s in the writes)`. No parameter, no template or DAG change: rebuild the image. Not yet run on a launcher.

### 🐛 Fixed
- The generation launch names its launcher VM: DAG param `launcher_machine_type` (default `e2-standard-8`, `environment.launcherMachineType`), as both evaluation launches already did. A five-table launch on Dataflow's default launcher (2026-10-12) spent 7 min 24 s of Google's 12 minutes pulling the image, had its graph built 11 min 19 s after it was accepted and was shut down 66 s into handing it over (`Timeout in polling result file`, no job submitted). Not yet run on a launcher ([RUN_PLAYBOOK §3](docs/RUN_PLAYBOOK.md#3-dataflow-options)).
- A chained or standalone evaluation launch reached the evaluator without its target: the Flex Template launcher drops a template parameter named `job_id`. The template parameter is now `generation_job_id` (`--job_id` still works on a direct command line); a test keeps template parameters clear of the names the launcher owns ([ADR 0041](docs/adr/0041-evaluation-standalone-package.md), note of 2026-10-08).
- **A run that is over does not stay Running.** The evaluation registry is append-only events: the launcher writes `RUNNING` before it submits the pipeline (the Dataflow job is queued meanwhile), the job writes `FINAL`. A chained evaluation whose launch died after `RUNNING` was written (the launcher's 12-minute limit, say) kept that row for ever, and the GUI listed it as Running. Two changes. (1) The generation DAG gains a fifth task, `wait_for_evaluation_launch` ([`composer/synthetic_beam_bigquery.py`](composer/synthetic_beam_bigquery.py)): a second status sensor, with the arguments `wait_for_generation` passes, that waits until the evaluation job runs (`JOB_STATE_RUNNING`, or `JOB_STATE_DONE` between two pokes; one poke a minute, an hour at most). The launch task cannot do this: it returns as soon as the job is queued, minutes before the launcher writes `RUNNING`. A job that ends any other way makes the sensor raise; once the task's retries are used up (the DAG sets none: Cloud Composer's default is two, five minutes apart, so about ten minutes later) its failure callback, `_close_running_row`, closes the row and logs how many rows it wrote: a copy of the standalone DAG's statement and guards, finding the row by this run's generation job id and the trigger `chained`. It writes `FINAL FAILED` only when the launched job ended without being done; for a job that is queued, running, done or unreadable it writes nothing. What it costs: the DAG run holds its one run slot until the evaluation's launch is over (at most the launcher's twelve minutes and one read of the job, plus the retries when the launcher died), and a dead evaluation launch now marks the DAG run failed (the run used to be green). It does not wait for the job's end, so a job that dies after a read saw it running is still not closed by the DAG. Not parsed or run by Airflow. (2) The GUI shows an evaluation whose last registry event is `RUNNING` and more than 24 hours old as **Stale**, not Running (the tables an evaluation prepares for its reads expire 24 hours after it creates them, so by then it has most likely ended without recording a result): the list's pill and phone cards, the run view's header, a callout under it and the empty state, the compare view and the INTRO counter. It is a display state derived in the browser; the registry's status stays `RUNNING` and no API, query or contract changed.
- **Seed retrieval picks the same items on Python 3.14 as on 3.11.** CPython 3.12 made the builtin `sum()` of floats a compensated sum. `sdfb_core.rag` summed with it in three places (`retrieval._sq_dist`, `index._normalize`, `_PyExactIPIndex.search`), so where candidates tie or nearly tie, the last bits of a distance decided the pick and the pick changed with the interpreter: the `kcenter` and `kcenter_rotate` seeds on grid-valued or hashed vectors, and the order of two parallel vectors in the pure-Python index. The default `centroid` arm on FAISS was not affected. The three sums are plain left-to-right loops, which is what 3.11 computed and what the GUI's TypeScript mirror computes; a regression test pins what 3.11 picked ([`test_retrieval_interpreter_parity.py`](packages/sdfb-tests/tests/unit/rag/test_retrieval_interpreter_parity.py)).
- **Two more values that Python 3.14 computed differently from 3.11, for the same reason** (the compensated builtin `sum()`). The preflight's `effective_cells`: for a reference sample whose PK categoricals are perfectly balanced, six equal cells gave 6.0 where 3.11 gave 5.999999999999999, and the FK key-sample cap, a `ceil()` of a quotient of it, came out one parent key lower (500,000 for 500,001): a different key pool changes every FK draw after it. And the `mean` of `source_table_stats`: its sixth decimal, where the mean is an exact tie there (10 of 240 seeded tables). Both sums are plain left-to-right loops, each with a test that pins the 3.11 value. The generator's other float sums (pattern-family shares, the IPF key weights and their cumulative, the expected duplicate share, entropy, stddev) move only in their last bits on 3.14: no draw, gate verdict or written value differed in the differential, so they are unchanged.
- **The evaluator's functions that summed floats with the builtin `sum()` return on Python 3.14 the bits they returned on 3.11.** Five of them did: `tvd_null_expectation` (the noise floor of the TVD family), `char_class_l1`, `shape_head_tv`, the reference side's `sum(c ln c)` behind the diversity baselines, and `chao_shen_bits` (called by tests only). They add left to right again, each with a test that pins a 3.11 value. No written value had moved: every float of a row is rounded to nine significant digits before it is written and graded, and the acceptance test's three evaluations write the same metric, profile and flag rows on both interpreters, before this change and after it ([ADR 0041, amendment of 2026-10-13](docs/adr/0041-evaluation-standalone-package.md#amendment-2026-10-13-python-314-and-beam-276-with-the-shared-image)).
- **A machine that resolves the dependencies again cannot settle on a pyarrow it would have to compile.** pyarrow comes in with Apache Beam, which accepts every release from 14.0.1; its first release with Python 3.14 wheels is 22.0.0. On a laptop whose own lock still held `pyarrow 18.1.0`, `uv sync --group dev` kept that version after the move to 3.14, tried to build it from source and stopped on `cmake`. Both projects now carry the uv constraint `pyarrow>=22` (root `pyproject.toml`, `packages/sdfb-evaluation/pyproject.toml`); the locked version is still 23.0.1 and no other locked package changed. `uv sync --frozen --group dev` installs exactly the committed lock ([`docs/M4_SETUP.md`](docs/M4_SETUP.md)).
- The evaluator's test of the generation DAG's markers accepts four more, for a deployment whose import workflow fills the defaults of `num_rows`, `uniqueness_mode`, `pool_seed_strategy` and `initial_workers` (`NUM_ROWS_DEFAULT`, `UNIQUENESS_MODE_DEFAULT`, `POOL_SEED_STRATEGY_DEFAULT`, `INITIAL_WORKERS_DEFAULT`). The committed DAG is unchanged and writes those defaults out; any other new marker still fails the test, and so does a missing one.

## [v0.3.0] — 2026-09-13

Relational generation by construction: a child is no longer a table that *happens* to hold valid foreign keys, it is generated *from* its parents' keys.

### 🚀 Added
- **Parent-driven fan-out.** Children are generated from their parent's landed keys: per key the engine draws the fan-out from the source histogram, draws the PK-completing categorical cells without replacement, copies inherited columns, and fills the rest through the existing samplers. Ratio, PK uniqueness and referential integrity now hold *by construction* ([ADR 0036](docs/adr/0036-parent-driven-fanout-generation.md)).
- **Multi-parent children.** A driven child may carry any number of independent edges (star-schema dimensions, served by a side-input key pool) and conditional edges (diamond branches, served by a co-partitioned `CoGroupByKey` on the shared columns). Star, diamond, tree, forest, 1:1 chain and arbitrary FK DAGs are all satisfiable; the only remaining launch stop in role derivation is two edges both marked `drives: true` ([ADR 0037](docs/adr/0037-multi-parent-children.md)).
- **The launch adjusts a model the source disproves.** Measuring the source can show the declared relationship model wrong; the launch widens the edge (`fk_edge_widened`), says so, and carries on instead of failing or silently obeying ([ADR 0038](docs/adr/0038-measured-conflicts-adjust-the-model.md)). Row projection happens before the graph is walked ([ADR 0039](docs/adr/0039-row-projection-before-the-graph.md)).
- **PK-capacity preflight that understands FK and categorical members.** An enforced FK inside a primary key counts once as the keys the child will see; unconstrained categoricals count their observed domain; random-draw tuples are judged against the run's BLOCKER gate, and the stop message names the largest gate-safe `--num_rows` ([ADR 0035](docs/adr/0035-pk-capacity-fk-bound-members.md)).
- New flags `--fk_candidate_cap`, `--driven_uniqueness_mode`, `--fk_fanout_stats_table`; new fan-out measurement cache `synthetic_data_quality.fk_fanout_stats`; `config/relationships/example_star_diamond.yaml`.
- `/e2e_fk_pk_validator` prompt — registry-derived contract plus read-only `bq` PK-duplicate, orphan and fan-out checks cross-read against `validation_runs`.

### 🔧 Changed
- `uniqueness_mode=streaming` (the default for driven children) now also measures `pk.duplicate`, so a driven child's PK guarantee is a measured fact rather than an argument.
- A child column may be written by exactly one edge. Two in-model edges that both own a column stop the launch and name the remedies; the same overlap between *external* edges only warns, since an external parent offers no remedy.
- Edge roles are derived rather than declared: with no `drives:`, the most-derived candidate parent drives and its edge is widened with the column pairs the child pins — no model edit needed to add a table.

### 🐛 Fixed
- Three false preflight stops: an FK member whose parent is disabled; `1 − exp(−x)` cancelling to a reported 100% duplicate share on a 3.6e27 pattern space; a true 1:1 child whose primary key *is* its driving edge.
- Per-key cell draws are O(k) on precomputed cumulative weights — 746 → 3.2 µs/key at 10k cells.

### 🗑️ Removed
- The 100k/1M FK side-input key cap and the in-DAG FK gate, for in-job driven edges. Both were workarounds for sampling keys a child cannot key by drawing; fan-out generation makes them unnecessary.

## [v0.2.0] — 2026-09-08

Throughput release. Same job shape (10M rows per table, one parent + one FK child, T4 workers), **93.8 min → 50.5 min** — see [ADR 0034](docs/adr/0034-generation-throughput-single-barrier-shared-engines.md).

### ⚡ Performance
- **Multi-process SDK containers** (`sdk_containers=multi`): generation was GIL-bound on one interpreter per worker with eight harness threads. A loopback-port spawn mutex lets one vLLM server per worker serve every SDK process — a 10k-row batch went from 26–29 s to **5.6–6.7 s**.
- **One dedup barrier instead of three** (`uniqueness_mode=exact`): PK/identity resolved from key-only collision groups as side inputs, rows packed as value tuples. Dedup + load per table went from 14.0 / 12.2 min to **3.4 / 3.0 min**, with identical DLQ envelopes and exact counts.
- **Process-shared engine registry**: 32 engine builds per table became one per process. The embedder now loads lazily, so a store-warm setup never opens a CUDA context beside vLLM.
- **Storage Read API for source domains**: a 944k-value identifier domain was being paged through the BigQuery REST iterator inside `DoFn.setup()` and read as a 5.5-min "generation stall".

### 🚀 Added
- `initial_workers`, `autoscaling=auto|throughput|fixed`, `sdk_containers=single|multi`, `rag_embed_shards` — template and DAG parameters, with run tiers `R7`/`R7m`.

### 🐛 Fixed
- The Storage Read API fallback re-iterated a consumed iterator, so on two acceptance runs *every* source-domain fetch failed and the pool rejection sets, identifier/numeric domains and pool-target sizing were silently inactive. The fallback now takes a fresh `QueryJob.result()`, with a per-process kill switch logged once.
- Fixed-width ceiling for mask-gated columns, which had let a 48-char value past a 35-char source ceiling.

### 🔧 Changed
- The worker service account now needs `roles/bigquery.readSessionUser`; without it each process pays one denied Storage attempt and falls back to REST.
- CPU population embeds under `multi` were **reverted** to the GPU (bounded to `rag_embed_shards`, with the pool branch waiting on the population): they had starved the model pull and vLLM init and turned a 2.9-min stage into 15.4 min.
